## 1. Scores — harshest-judge reasoning

| Criterion | Score |
|---|---|
| Technological Implementation | **6/10** |
| Design | **7/10** |
| Potential Impact | **7/10** |
| Quality of Idea | **7/10** |
| **Average** | **~6.8/10** |

**Technological Implementation — 6/10.** "Your pipeline is: small model drafts text, big model reads the text, a search API looks up a clinic. That's the same three costumes BoardBrief wore." The judge's specific attacks: (a) Ultra's job — "cross-check for missed barriers" — is *unverifiable as pitched*. How would anyone know Ultra caught something the first pass missed? No eval, no ablation, no number = costume, exactly the round-1 mediocre band. (b) The genuinely hard technical problems of this domain — a barrier taxonomy with schema-validated structured extraction, bilingual fidelity checking, a safety classifier that routes cases — are *implied*, not specified. If they get built and measured, this is a 7–8. If the build ships prompts and hope, it's a 5. (c) "WhatsApp-style" is doing quiet work in the pitch: there is no messaging integration, no identity, no delivery — it's a web chat with two panels. Fine, but don't let the README imply more.

**Design — 7/10.** This is the idea's second-best criterion and the reason it beats BoardBrief. The split-screen draft → edit → approve → send is a *complete product workflow for two named users*, and the state change is visible in every frame — the exact thing round 1 demanded ("ship two features that are flawless"). Harshest objections: (a) Two user surfaces in 8–10 solo build days is the scope-sprawl failure mode wearing a good suit — the likeliest Oct 30 outcome is a polished patient side and a navigator panel that looks like an admin afterthought, and Design punishes the weaker half. (b) Text chat is a questionable interface for the actual audience: low-literacy, older, post-diagnosis patients typing long Spanish messages on phones. A judge who knows this population will ask why there's no voice input — and "not in scope" is a weak answer when the entrant's own design notes for Podrá center accessibility. (c) If the UI is a default chat skin, it drops to 5 instantly.

**Potential Impact — 7/10.** The strongest *case* in the shortlist and still capped at 7, for one reason round 1 already named: **zero real-user evidence**. Named audience ✓ (Spanish-speaking LCC patients), named org ✓, problem that is expensive when it goes wrong ✓ (a missed biopsy or a patient who never arrives is delayed cancer care, not inconvenience). But: the demo patients are fictional, no navigator has touched it, there is no number anywhere — not LCC navigation caseload, not minutes-per-case today vs. with the tool, not missed-appointment rates. A harsh judge reads the pitch as *"a letter of intent from the org's own chair."* That last phrase is also the conflict a judge may quietly hold against it: the builder chairs the beneficiary org, so his enthusiasm is not independent validation. One named navigator's timed test + quote moves this to 9. Without it, impact is asserted by the single most interested party.

**Quality of Idea — 7/10.** The non-obvious insight is real, and it's the best one in the swarm's set: *navigation doesn't fail on information, it fails on unasked barriers — the ride, the cost, the childcare, the fear — so the AI's job is barrier hunting, and the human's job is judgment; the machine is never allowed to speak to the patient alone.* A judge can repeat that in one sentence afterward. It loses points because: (a) "AI copilot drafts, human approves" is a rapidly standardizing 2026 pattern, and health-navigation chatbots are a crowded hackathon genre — the insight is in the barrier taxonomy + approval gate, not in the category, and the pitch must say so or it reads as genre entry #400; (b) this is a pre-existing plan being carried into a hackathon. Rules allow it with a written significant-update explanation — but on *Idea* specifically, a judge may discount novelty when the submission itself discloses the design predates the period. The honest framing (plan = documents; new in period = working Nebius system, barrier engine, evals) is the only defense.

## 2. The 3 kill-shot objections

**KILL SHOT 1: "This is a medical-advice machine with a rubber stamp on it."**
The navigator approves drafts. We know what approval fatigue looks like: by case thirty, the navigator taps Approve in four seconds. Now the AI's hallucinated prep instruction or stale clinic hour is *patient-facing medical communication from a real cancer nonprofit*, with the entrant's name on it as chair. **Answer — only evidence, no argument:** (a) an adversarial safety battery (≥20 prompts: medication changes, symptom emergencies, diagnosis requests, prognosis questions) with a published result — the system must refuse to *draft* on all of them and escalate instead; (b) guardrails as visible system state (see §4): Approve is *disabled* while a message contains an unverified resource; medical facts in drafts come only from pre-approved source text shown with its source. If the team cannot run and publish this battery, this objection is **unanswerable and the idea should be killed on safety/reputation grounds alone**, regardless of score.

**KILL SHOT 2: "ChatGPT with an Approve button."**
A patient message goes in, a kind plain-language Spanish reply comes out. A general chatbot does that today, in good Spanish, for free. **Answer:** a *measured barrier-detection number*. Build 10–15 annotated fictional cases with planted barriers (transport, cost, childcare, work schedule, fear, language, health literacy). Run Podrá's full pipeline and a single plain prompt to a general chatbot on identical inputs. Publish: *"Podrá's barrier audit caught X of Y planted barriers; the baseline caught Z."* Plus show the artifacts a prompt doesn't produce: the persistent barrier checklist per case, the escalation note, the signed approval record. If the catch-rate gap is small or unmeasured, this objection is simply true and the idea is a wrapper with better intentions.

**KILL SHOT 3: "Fictional patients, no deployment, and the org hasn't actually adopted this — impact is theater."**
Compounds: judges can smell synthetic (round 1), and here synthetic is *mandatory* — real patient data is off-limits, correctly. So the demo can never show the real thing. **Answer:** move the reality one step sideways — a real *navigator* instead of real patients. LCC's actual patient-navigation lead runs the tool on the fictional cases before Oct 30: timed drafting time manual vs. with Podrá (the before/after number), a named quote or short clip, and a letter/statement that LCC's leadership is aware the org is named in this entry. That last item is not optional decoration: naming a real nonprofit and its patient population in a public submission without the org's knowledge is a governance problem for its own chair. Answerable — but it depends on other people's calendars, which makes it a schedule risk, not a build risk (see Bar 7).

## 3. Round-1 Oct 18 kill bars, applied to Podrá

1. **Stack bar — MODERATE RISK.** Two+ Nemotron tiers doing logged, real work in one run by Oct 18 is achievable. The trap is Ultra-as-costume. *Test:* ablation on the annotated case set — pipeline with and without the Ultra barrier-audit pass. If barrier recall doesn't measurably drop without Ultra, the stack bar is failed in spirit even if two models were called.
2. **Baseline bar — HIGHEST RISK.** Blind A/B risk is worse than for BoardBrief in one specific way: judged on *reply text alone*, Podrá ties a plain chatbot — same language, same kindness, same questions list. It only wins if the A/B scores the **full case output** (barrier checklist, escalation routing, approval record, resource verification state). *Test:* 3 readers, same patient inputs, Podrá full case file vs. baseline chat transcript, asked "which output would you trust a navigator's office to run on, and what concrete thing does one have that the other lacks?" If readers can't name the artifact advantage unprompted → dead.
3. **Accuracy bar — HIGH RISK, Podrá-specific form.** Round 1: planted-error detection <50% = kill. Translated: **barrier recall <50% on the annotated planted-barrier set = kill.** Plus a second, zero-tolerance accuracy bar this idea carries that BoardBrief didn't: **any medical-advice slip in the safety battery (a drafted answer to a diagnosis/treatment/medication question, a hallucinated prep instruction) = fail until fixed and re-run clean.** Resource facts (clinic hours, phone numbers) in the demo set must be verified at authoring time and dated.
4. **Reliability bar — MODERATE RISK.** Each case is 3–6 model calls + Tavily. Spanish generation quality will vary run to run; a demo case that produces a subtly wrong draft on camera is worse than a hang. *Test:* the standard 20 consecutive end-to-end runs, plus a fixed 5-case golden set whose outputs a bilingual reviewer scores for correctness/register — not just "did it complete."
5. **Cost bar — LOW RISK.** Cheap tiers do volume; one Ultra call per case on condensed context. The one leak: Tavily per message. *Rule:* resource lookups come from a cached local resource directory; Tavily verifies/refreshes, max 3 calls per case, cached by query. 200 judging runs fit the $50 stack comfortably if Ultra never sees raw history.
6. **Rights bar — PASSES, and it's this idea's structural advantage.** Fictional patients are legally showable, realistic, and producible — the exact bar BoardBrief nearly failed on confidential packets. The cost is paid in Impact credibility (Kill Shot 3), not in rights.
7. **Scope bar — HIGH RISK.** Components: patient chat, navigator panel, case/barrier state, escalation routing, Tavily verification, bilingual generation, safety layer, eval harness. Services count is fine (Token Factory + Tavily = 2), but *unbuilt-component* count is the real count, and the safety battery + eval harness are each close to the 2-day limit by themselves inside an 8–10 day total budget. *Pre-declared cuts (make them now, not on Oct 18):* single case flow end-to-end; navigator "queue" is a list, not a workflow; no voice input; no multi-patient history beyond the one demo case file. If cutting the eval/safety harness is ever proposed to save the schedule — that's the kill signal, per Kill Shot 1.

## 4. Health-safety attack — what can hurt someone, and what must be VISIBLE

Failure paths, in severity order:

- **Emergency delay.** A patient writes about fever during chemo, bleeding, or crisis/self-harm. Any design where the system *starts drafting a reply* to that message has already failed — minutes matter and a chat draft is the wrong artifact entirely. **Visible guardrail:** the escalation detector fires *before* drafting; the patient side immediately shows a red banner in Spanish directing her to call 911 / her care team now, and the case jumps the navigator queue flagged red. This sequence must be *in the demo video*, ~15 seconds, unprompted by the narrator.
- **Hallucinated medical preparation.** "You need a biopsy" → a draft that invents fasting/medication prep could cause a cancelled procedure or harm. **Visible guardrail:** drafts may only state medical facts drawn from pre-approved source snippets, displayed in the navigator panel *with the source attached to the sentence*. If there's no approved source for it, the draft says the navigator will confirm — and the panel shows that gap.
- **Stale/ hallucinated resources.** Tavily returns a clinic that changed hours, a support group that folded, a wrong phone number — and a cancer patient with no car rides across town to a closed door. This is the most *likely* harm in the set. **Visible guardrail:** every resource in a draft carries source + last-checked date, and **the Approve button is disabled until the navigator checks the "verified" box for each resource in the message.** A disabled button is a guardrail. A paragraph saying "navigators verify resources" is a claim.
- **Rubber-stamp approval.** Covered in Kill Shot 1. **Visible guardrail:** the approval panel forces attention where it matters — barriers found and unverified items are highlighted *in the draft itself*, approval requires resolving the highlights, and the approval record (who, when, what was edited) is shown as a product artifact, not hidden in a log file.
- **Privacy.** Chat logs about a cancer diagnosis are among the most sensitive data a person has. The demo is fictional — **the words "pacientes ficticios / fictional patients" must be on screen in the demo itself**, not just the Devpost text, both for honesty and so no judge wonders. The product story must also not require patient names/identifiers: case IDs, not identities.
- **Reputational blast radius (entrant-specific).** Jose Luis is not an anonymous builder here — he chairs LCC. A single frame of video showing "his" AI confidently misstating something medical will outlive this hackathon and attach to him and the org. This is why the safety battery (§2.1) is prioritized above every feature: the downside of this idea is not a low score, it's a screenshot.

## 5. The blind A/B question — answered honestly

**What Podrá does that a plain prompt structurally does NOT:**

1. **Persistent case state.** A barrier checklist and case file that accumulate across messages and sessions. A prompt produces a reply; Podrá produces a *case* that a second human can pick up cold.
2. **An enforced second human.** The draft is *blocked* from the patient until a different person approves it, producing an auditable approval record. A chatbot prompt cannot enforce its own supervision — the same person prompting is the person "approving."
3. **A systematic barrier sweep.** Every case is audited against a fixed barrier taxonomy, whether or not the patient mentioned the barrier. A baseline prompt finds the barriers it happens to notice; the sweep's value is measurable recall (and measurable is the whole game — see Kill Shot 2).
4. **Escalation as system behavior**, including the pre-draft crisis path — routing is state, not prose.

**The honest weakness:** none of that lives in the *text of any single reply*, and the reply is what a casual judge sees first. Strip the workflow away and Podrá's prose is a chatbot's prose. The structural difference is **real but narrow** — it is a workflow-and-measurement moat, not a capability moat. Score it accordingly: it survives the baseline bar only if the submission *leads* with the artifacts and the catch-rate number. If the video opens on the chat, it loses the A/B before the approval panel ever appears. **Open the video on the navigator's screen, not the patient's.**

## 6. FINAL VERDICT: **PASS WITH FIXES**

As pitched: **~6.8/10 — mid-pack-plus in a 21,107-person field. No prize.** The idea survives because its Impact case and its visible workflow are genuinely above the wrapper line, and because the rights bar — the quiet killer — is cleanly passed. It does not get a clean PASS because its two load-bearing claims (Ultra catches missed barriers; a human's approval makes this safe) are currently *assertions with no measurement and no enforced mechanism behind them*.

**Fixes, in priority order:**

1. **Safety battery + visible guardrails** (Kill Shot 1, §4): ≥20 adversarial prompts, zero drafts on medical-advice categories, pre-draft crisis escalation, Approve disabled on unverified resources, approved-source-only medical facts. *Non-negotiable — if this can't be done in budget, KILL and fall back to ClearRead.*
2. **Barrier-detection eval with a published number** (Kill Shot 2): 10–15 annotated fictional cases, planted barriers, Podrá catch rate vs. single-prompt baseline, plus the Ultra ablation result. This one artifact raises Tech and Idea simultaneously.
3. **Real navigator evidence** (Kill Shot 3): LCC's navigation lead runs the tool on the fictional cases — timed before/after, named quote/clip — and LCC leadership awareness of the org being named is on record.
4. **Lead the demo with the workflow, not the chat:** video opens on the navigator panel and the barrier audit screen; cost/latency/model-ID table in the README per round-1 rubric.
5. **Pre-declared scope cuts** (Bar 7): one case flow flawless; cached resource directory with Tavily as verifier (≤3 cached calls/case); no voice, no queue workflow, no real WhatsApp.
6. **Written significant-update framing** for the pre-existing Podrá plan in the submission text: what existed before Aug 26 was design documents; everything running is new in the period.

**Honest prize ceiling:** With all six fixes landed and the eval number strong, the ceiling is the **Best Apps and Agents track prize (Jetson) plus one bonus — Tavily $3,000 is the natural bonus target, SF City $500 also live** (stacking rules allow one overall-or-track + one bonus). An overall 3rd ($6,000) is a stretch outcome, not a plan. **Grand Prize: no** — round 1's prediction stands; the very thing that makes Podrá safe (a human gate on every action) deliberately caps the end-to-end autonomous spectacle Grand Prize demos are made of. Aim it at track + Tavily, deliberately, and it is a credible prize entry. Ship it as pitched, and it is a well-intentioned mid-pack entry with a safety story a good judge will dismantle in one question.
